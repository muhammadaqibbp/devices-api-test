# Devices API

A REST API for persisting and managing device resources, built with C# 14 / .NET 10, ASP.NET Core, EF Core and SQL Server.

## Quick start

### With Docker (recommended)

Requires Docker with Compose.

```bash
docker compose up --build
```

- API: <http://localhost:8080>
- Swagger UI (interactive API documentation): <http://localhost:8080/swagger>
- OpenAPI document: <http://localhost:8080/swagger/v1/swagger.json>
- Health check: <http://localhost:8080/health>

The database password defaults to a development value; override it with `MSSQL_SA_PASSWORD=... docker compose up --build` (SQL Server requires a complex password: 8+ characters with upper/lower case, digits and symbols).
Data is kept in the `devices-db-data` volume. Remove it with `docker compose down -v`.

### Locally

Requires the .NET 10 SDK and a SQL Server instance.

```bash
docker compose up -d db                 # start only SQL Server
dotnet run --project src/DevicesApi     # http://localhost:5080/swagger
```

The default connection string in `src/DevicesApi/appsettings.json` matches the Compose database.

## Domain

| Field         | Type                                  | Notes                                       |
|---------------|---------------------------------------|---------------------------------------------|
| `id`          | GUID (version 7)                      | Generated by the server                     |
| `name`        | string, 1-200 chars                   | Trimmed, required                           |
| `brand`       | string, 1-100 chars                   | Trimmed, required                           |
| `state`       | `available`, `in-use`, `inactive`     | Defaults to `available` on creation         |
| `creationTime`| ISO 8601 timestamp (UTC)              | Set by the server, immutable                |

## API

Base path: `/api/devices`. Full, interactive documentation is available in Swagger UI.

| Operation                    | Request                                      | Success | Errors             |
|------------------------------|----------------------------------------------|---------|--------------------|
| Create a device              | `POST /api/devices`                          | 201     | 400                |
| Fetch a single device        | `GET /api/devices/{id}`                      | 200     | 404                |
| Fetch all devices            | `GET /api/devices`                           | 200     | 400                |
| Fetch devices by brand       | `GET /api/devices?brand=Apple`               | 200     | 400                |
| Fetch devices by state       | `GET /api/devices?state=in-use`              | 200     | 400                |
| Fully update a device        | `PUT /api/devices/{id}`                      | 200     | 400, 404, 409      |
| Partially update a device    | `PATCH /api/devices/{id}`                    | 200     | 400, 404, 409      |
| Delete a device              | `DELETE /api/devices/{id}`                   | 204     | 404, 409           |

`brand` and `state` can be combined, and the list is paged with `page` (default 1) and `pageSize` (default 20, max 100).
The list response is `{ "items": [...], "page": 1, "pageSize": 20, "totalCount": 42, "totalPages": 3 }`, ordered by creation time.
Brand matching is case-insensitive and exact. State accepts `available`, `in-use` (also `in_use`, `inuse`) and `inactive`.

### Examples

```bash
# Create
curl -X POST http://localhost:8080/api/devices \
  -H "Content-Type: application/json" \
  -d '{"name": "iPhone 15", "brand": "Apple", "state": "available"}'

# List by brand and state
curl "http://localhost:8080/api/devices?brand=apple&state=available"

# Partial update (only the state)
curl -X PATCH http://localhost:8080/api/devices/<id> \
  -H "Content-Type: application/json" \
  -d '{"state": "in-use"}'

# Full update (all fields required)
curl -X PUT http://localhost:8080/api/devices/<id> \
  -H "Content-Type: application/json" \
  -d '{"name": "iPhone 15 Pro", "brand": "Apple", "state": "available"}'

# Delete
curl -X DELETE http://localhost:8080/api/devices/<id>
```

### Errors

Errors follow RFC 7807 (`application/problem+json`) and include a `traceId`.

| Status | When                                                                                          |
|--------|-----------------------------------------------------------------------------------------------|
| 400    | Invalid or missing fields, unknown state, unknown JSON properties (e.g. `creationTime`), bad paging |
| 404    | The device does not exist                                                                     |
| 409    | A business rule blocks the operation, or the device was changed concurrently                   |
| 500    | Unexpected error (details are logged, never returned)                                          |

## Business rules

| Rule                                                       | Where it is enforced                          | Result |
|------------------------------------------------------------|-----------------------------------------------|--------|
| Creation time cannot be updated                            | `Device` has no way to change it; update payloads do not accept it and unknown properties are rejected | 400 if sent |
| Name and brand cannot be updated while the device is in use | `Device.Update`                              | 409    |
| In-use devices cannot be deleted                           | `Device.EnsureCanBeDeleted`                  | 409    |

## Architecture

A single ASP.NET Core project organized in layers, with dependencies pointing inwards:

```
src/DevicesApi
├── Domain           Device entity, DeviceState, domain exceptions (no dependencies)
├── Application      DeviceService, DTOs, repository contract (depends on Domain)
├── Infrastructure   EF Core DbContext, mapping, repository (depends on Application)
└── Api              Controller and exception handling (depends on Application)
tests/DevicesApi.Tests
├── Domain           Entity rules
├── Application      Service and parser behaviour with a mocked repository
└── Integration      Full HTTP pipeline against a temporary SQLite database
```

Key choices:

- **Rules live on the entity.** `Device` guards its own invariants, so no code path can bypass them.
- **Optimistic concurrency.** A `Version` column is the EF concurrency token, so a concurrent update or delete cannot silently
  override another one; the loser receives `409`.
- **Time is injected** (`TimeProvider`) so creation time is deterministic in tests.
- **Consistent errors.** A single `IExceptionHandler` maps exceptions to problem responses.
- **Strict payloads.** Unknown JSON properties are rejected rather than silently ignored.

## Testing

```bash
dotnet test
```

With coverage (collected via `coverlet.collector`):

```bash
dotnet test --collect:"XPlat Code Coverage"
```

- **Unit tests** cover the entity rules, the state parser and every service operation (success, not found, validation and rule violations).
- **Integration tests** run the real application against a temporary SQLite file and verify status codes, serialization, filters, paging,
  update and delete rules, rejection of `creationTime`, and the health and OpenAPI endpoints.
  SQLite is used only by the tests; the application itself persists to SQL Server.

## Configuration

| Setting                         | Default                                   | Description                                |
|---------------------------------|-------------------------------------------|--------------------------------------------|
| `ConnectionStrings:Devices`     | local SQL Server (see `appsettings.json`)  | Database connection string                 |
| `Persistence:Provider`          | `SqlServer`                               | `SqlServer`, or `Sqlite` for tests/dev     |

Any setting can be overridden with environment variables, e.g. `ConnectionStrings__Devices`.

## Assumptions and design decisions

- **In-use lock is evaluated against the current state.** If a request changes `name` and also moves the device out of `in-use`
  in the same call, it is rejected. Move the device out of use first, then rename it.
- **Re-sending unchanged values is not an update.** A `PUT` on an in-use device that repeats the current name and brand and only changes the state succeeds.
- **`PATCH` treats an omitted field and an explicit `null` the same way** (no change). An empty patch is rejected with 400.
- **Updating `creationTime` is a client error** (400) instead of being silently ignored, so mistakes are visible.
- **State is serialized as lowercase kebab-case** (`in-use`), matching the requirement wording.
- **Paging is applied to the list endpoint** so large datasets cannot be returned in one response.
- **Swagger UI is enabled in every environment** so the documentation is available from the container. Disable it in `Program.cs` if the API is exposed publicly.

## Known limitations and future improvements

- **EF Core migrations.** The schema is created with `EnsureCreated` at startup, which is fine for a first deployment but cannot evolve an existing database.
  Next step: add `Microsoft.EntityFrameworkCore.Design`, generate an `InitialCreate` migration and call `Database.MigrateAsync()` at startup (or run migrations as a deployment step).
- **Brand filtering** uses `LOWER(brand)`, which prevents index seeks on the brand index. SQL Server's default collation is already case-insensitive, so at scale drop the `ToLower()` and rely on the collation (or add a computed, indexed column).
- **GUID keys.** Ids are version 7 GUIDs; SQL Server orders `uniqueidentifier` differently from the byte order, so the clustered index does not get fully sequential inserts. Consider a separate clustered key if write volume grows.
- **Authentication and authorization** are not implemented.
- **Package versions** use floating patch ranges (e.g. `10.0.*`); pin them with a lock file (`RestorePackagesWithLockFile`) for reproducible builds.
- **Observability.** Add structured logging sinks, metrics and distributed tracing (OpenTelemetry).
- **Rate limiting and CORS** are not configured.
- **Soft delete / audit trail** of device state changes could be added if history is needed.
